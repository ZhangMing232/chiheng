| 但 | `migrations/` 只有 `0001_auth.sql` / `0002_membership.sql`，**业务代码里没有一处 `getSql()` 调用**——数据库是装好没接线 |

**我的建议：不迁 SQLite，理由不是「麻烦」是「收益对不上风险」**：
- 129 KB 的账本完全没有 JSON 的性能问题；真正的问题是**全量读改写的并发窗口**——
  临时名带 pid 只防了「两个进程写同一个 tmp 文件」，没防「A 读 → B 读 → A 写 → B 写」
  的丢更新（B 的整本覆盖掉 A 刚记的一笔）。这是**现存真风险**，和换成什么存储无关。
- 每天 23:30 已有全量快照（留 5 份）、`journal-backup.ts` 有写前备份，容灾不靠存储引擎。
- 要迁，更自然的是**接上项目已有的 PGlite**（Postgres 语义、零新增依赖），而不是新引
  SQLite 方言；但那要动账本读写契约 + 迁移 316 笔 + 双写灰度，是几天量级的活。

**待拍板的三个选项**：
- A（我倾向）：**不迁**。先补并发（文件锁或单写者）+ 写前版本校验，沿用 JSON + 现有备份。成本最低，直接消掉真实风险。
- B：接已有 PGlite，账本进 SQL 表，JSON 留作导出/备份，双写灰度一个周期再切。
- C：新引 SQLite（better-sqlite3 等）。除非有明确要 SQL 查询账本的需求，否则和 B 重复造轮子。

### 12.2 流水轮转：**根因不是「文件会一直长」，是每分钟写同一句重复日志**

| 项 | 实测 |
|---|---|
| `gate-blocks.jsonl` | 1.64 MB / 6721 行 / 2026-10-08~11-06（29 天），244 B/行 |
| 增速 | 每个交易日稳定 **240 条**（≈ 57 KB/交易日，按 250 交易日算 ≈ **14 MB/年**；21 个交易日已攒 1.6 MB） |
| **去重后** | **唯一签名只有 621 条（9.2%）**，最重复的一条被写了 **249 次** |
| 今天 | 52 条里 51 条是同一句「交易日记录 17/60，样本还不够下结论」 |
| 读方 | **生产代码只写不读**——`readGateLogs()` / `hardBlocksOn()` 只有测试在调，页面没有消费方 |

**根因**（`scripts/record-journal.ts:509` 附近）：提示闸的 `buysPresentThisRun` 标志想
「样本不够只记一笔」，但记账进程**每分钟新起一个**，标志每次都是新的，于是每分钟
都写一条完全一样的 soft 记录。`gate-log.ts` 文件头注释还写着「写入频率低（只被拦时写）」，
已经和现实矛盾。

**我的建议：先去重，再谈轮转**。轮转 1.64 MB 的文件解决不了「每天 240 行噪声」；
把「同一交易日 + 同 style + 同 gate + 同 reason」写成一天一条（带 `count` 字段记次数），
文件一年只长几十 KB。去重之后：
- 若还要轮转：按月切 `gate-blocks-YYYY-MM.jsonl`，保留 12 个月 + 归档压缩，读取方按日期找文件。
- 但**当前没有生产读取方**，轮转的收益只是磁盘和备份体积；真正的价值是让这份
  「风控拦了什么」的证据变得可读（现在 90% 是噪声，没法复盘）。

**待拍板**：① 只去重（我倾向，改 `appendGateLog` 一处 + 测试）；② 去重 + 按月轮转；
③ 只轮转不去重（不推荐，噪声原样搬进归档）。

### 12.3 AI 超时治理：**150 秒硬超时正在常态化掐掉调用**

| 项 | 实测 |
|---|---|
| 现状 | `callAI` 每档案 150 s `AbortController`；`callAIWithFallback` 主档案失败切下一个；`ai-retry.ts` 有同指纹熔断（连败 2 次拒发、24 h TTL）；DSH 优先通道 |
| `ai-usage.json` | 224 次调用，**49 次 `ok=false`（21.9%）**，其中 **37 次耗时 ≥149 s = 超时被掐** |
| 耗时分布 | 中位 55.8 s / p90 150.0 s / p95 150.0 s / max 150.1 s |
| **口径不一致** | `ai-log.json` 只记 **9 条失败**（8%），`ai-usage.json` 记 49 条——因为上层 fallback 成功后整轮算 `ok`，中间被掐的那次只在 usage 里留痕。**看 ai-log 会严重低估超时** |
| 历史失败 | 9 条里 5 条 `This operation was aborted`、2 条 `fetch failed`、1 条 429、1 条 400(temperature) |
| **洞** | **`chiheng-dsh-client.ts` 的 `callDSH` 完全没有超时**（fetch 无 signal）；而 `callAIWithFallback` 开头先无条件走 DSH，桥接挂住会把整轮进化拖死，且绕开 150 s 超时和 fallback |

**我的建议（按性价比排）**：
1. 给 DSH fetch 加同样的超时（裸 fetch 无任何 signal，桥接挂住会拖死整轮）——**这属于「AI 超时治理」大件，等拍板再动，本轮一行代码没改**。
2. **层间超时差异化**：factor 层 90~120 s 就切档案（现在等满 150 s 再切，一轮白等 2.5 分钟）；
   agent 全局诊断 prompt 最长可留 180 s。
3. **超时可观测**：`ai-log` 记每次尝试的耗时/失败原因，别让 fallback 成功掩盖中间的超时。
4. 熔断已有，但只按 prompt 指纹；超时类失败应单独计数（模型慢 ≠ 这句话有问题）。

**待拍板**：超时策略改到什么程度（只修 DSH / 加分层超时+可观测 / 顺带重做重试退避）。
注意这会改自动进化的行为，属于「改 AI 闭环」，要带 `allowRealGenome` 护栏那套验收。
