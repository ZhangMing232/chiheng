> 注：规划时（写本计划当天）账本当天只有 3 笔、重合 1 只；落地的 `reconcileDay` 是**按实时账本现算**，

关键代码事实：

- `/today` 的三路矩阵在 `src/routes/today.tsx:220-260` 由三份数据拼成：
  前瞻 `forecast.locked[0].picks`、短线 `reviewed.signals(leg=short).slice(0,8)`、
  中长线 `reviewed.signals(leg=long).slice(0,8)`。
- `getSignalReviewed`（`src/lib/market/quotes.functions.ts:1865`）在服务端**用当天 K 线现算**
  `order`（下单价）和 `fill`（理论成交：开盘价 ≤ 下单价 / 最低价触到 / 没触到），
  **只回给页面，不落盘**。所以页面上的「成交」是**事后按日 K 理论重算**，
  不是账本里当时记下的真实成交。
- 账本 `getServerJournal`（同文件 `:752`），结构 `days[].trades[]`，字段
  `id / code / name / entry / stop / target / style / hold / exit / exitDate / variant / deepScan`。
- 记账建仓 `scripts/record-journal.ts:564-571` 自己再扫一次 universe → `watchList` → `takeBuys`，
  **不读 `reviewed.json`**。两次扫描时点、过滤条件都不同，产出自然不同。

🔴 **本计划最重要的一条纪律**：理论成交（`fill`，事后按日 K 重算）与真实成交
（账本 `entry`，当时记下）**必须分开标注，不许互相冒充**。这是用户立的
A 股成交铁律第 4 条，也是这套对账不能做成「拿 K 线把账本补一遍」的原因。

## 1. 目标与验收

**目标**：同一个交易日，「今天说了什么」和「后来真买了什么」在两页对得上；
用户看完 `/today` 去策略追踪，能一眼看出哪几只买了、哪几只没买、为什么。

**验收（用 11-13 的真实数据跑）**：
1. `/today` 每只票显示「账本已买 / 未买」，账本已买的显示真实成交价 `entry`。
2. 策略追踪有一块「今天 /today 说了什么」，列出 20 只信号、当天账本真实成交笔数、重合只数，
   以及 `账本买了但 /today 没提` 的票，三类和数字都如实给出（数字由 `reconcileDay` 实时算，见第 0 节末态）。
3. 两页都不把「理论成交」写成「真实成交」，各自标清口径。
4. 读不到数据一律 `null + 原因`，不补 0、不拿空数组冒充。
5. `npm test` 全绿、两页 CDP 0 水合/运行时报错、冒烟 0 FAIL。

**不做**：不改任何实际建仓行为，不写回 `reviewed.json` 或账本，不动侧栏六组，
不动落档文件（前瞻落档后不许改）。

## 2. P0 · 对账（建议本轮做，纯展示层）

### P0-1 抽一个纯函数模块

新建 `src/lib/market/daily-reconcile.ts`：

```
reconcileDay(signals, journalDays, date) -> {
  date,
  signalRows:  [{ code, name, leg, orderPrice, fillStatus, bookTrade | null }],
  matched:     [...],   // 两边都有
  signalOnly:  [...],   // /today 有、账本没买
  bookOnly:    [...],   // 账本买了、/today 没提
  missing:     string | null,   // 数据读不到时写原因，不编
}
```

- **关联键**：六位 `code` + `date`。前瞻 `picks` 的 code 带 `sh/sz/bj` 前缀，
  `/today` 已用 `replace(/^(sh|sz|bj)/,"")` 处理，统一沿用。
- 纯函数、零 IO、不取当前时间 —— 项目里「源码字符串守门会假红」的教训，
  把逻辑抽成真模块让测试直接 import 算一遍，别在测试里断言源码字符串。
- `bookTrade` 只带展示需要的字段（entry / exit / style / variant），不把整本账传进页面。

配套 `src/lib/market/daily-reconcile.test.ts`：
- 三分类正确性（用 11-13 真实数字造 fixture：20 / 3 / 1）；
- code 去前缀、日期不匹配不算重合；
- 当天账本缺失 → `missing` 写明原因，**不返回空数组冒充「没买」**；
- `fillStatus !== 账本成交`：断言理论成交字段永远不会被当成 `entry`；
- 同一只当天多笔账本成交不重复计数。

### P0-2 `/today` 回填账本状态

- `src/routes/today.tsx` loader 的 `Promise.all` 增加 `getServerJournal().catch(() => null)`。
  读不到返回 null，页面显示「账本暂时读不到」而不是「未买」。
- 调 `reconcileDay(...)`，在矩阵每行加一列「账本」：
  `已买 56.70` / `未买`（`已买` 用账本 `entry`，**不用** `fill.fillPrice`）。
- 顶部徽标「可买 N / 放弃 M」改成不混淆的两组数字，或加一行说明：
  「信号 N 只 · 账本今日成交 M 笔」。原来的「可买」是信号口径，别让它看起来像成交数。
- 复用刚加的「口径 // …」说明条样式，写清：
  「本页成交状态来自账本当时记录；挂单价/理论成交是按日 K 事后重算，两者不是一回事」。

### P0-3 策略追踪加回看区

- `src/routes/strategies/positions.tsx` loader 增加 `getSignalReviewed().catch(() => null)`。
- 在 `PageTabs`（`:1079`）里加一个 tab「今日对照」，或在「跟单」tab 顶部加一块，
  二选一由用户定；内容是同一份 `reconcileDay` 结果的三个分类清单。
- 只展示，**不提供任何「补买 / 同步到账本」按钮** —— 这轮不做写操作。

**P0 完成后**：两页对得上账，但选股行为一点没变。可直接验 11-13 数据。

## 4. P2 · 两链合一（**2026-11-13 评估完毕，裁决：不做**）

> 原设想：让 `reviewed.json` 成为账本唯一候选源，`record-journal.ts` 不再自己扫 universe，
> 两链合成一条。前置要求「P0 上线后观察一段真实交易日，拿对账数据看清差在哪」。
> **该前置已完成**：[`P2-RECONCILE-REPORT.md`](</Volumes/colorful/chiheng/design/P2-RECONCILE-REPORT.md>)，
> 复跑脚本 `scripts/reconcile-p2.ts`（只读，直接调线上 `reconcileDay`）。

**实测（5 个交易日 / 100 只次信号 / 37 笔账本成交 / 重合 6 只）**：31 笔「账本买了、
/today 没提」逐笔归因后是 **16 笔挑战者·深扫实验 + 15 笔盘中新增扫描**，
**0 笔属于算错或丢单**；反向 94 只次「/today 说了没买」里有 50 只次是 short 腿
（热点·题材补涨 = `relay`），该策略在 `RETIRED_STYLES` 里明文「不再建仓」，0 命中是设计使然。

**结论：差得有道理，两份名单服务的不是同一个问题** —— `/today` 是 09:26 竞价审核后的
当日提案，账本是一整天里所有真实成交（含实验田、含盘中新增）。合一的四个前置问题
（名额/T+1 与 skip 对齐、盘中新信号、`reviewed.json` 只覆盖早盘、回测+双闸）
不是「待解决」，而是「两链本来就分工不同」；强行对齐会删掉实验田样本、删掉盘中、
把已淘汰的 `relay` 拉回账本。**P2 不做，保留双链 + 显式口径。**

真正值得做的下一刀见报告 §5：把「账本独有」三类归因做成页面标签、给 short 腿标
「观察·不建仓」、给账本 `days[]` 无序加守门测试、每日自动落一份对账快照。
